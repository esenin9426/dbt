# 14 — Итоговый проект

## Цель

Самостоятельно расширить этот проект до состояния, которое можно
показать работодателю или ученикам как доказательство того, что вы
реально умеете работать с dbt — а не просто прошли готовые шаги.

## Задание

Выберите **один** из двух вариантов (или предложите свой, близкий по
объёму):

### Вариант A — Новый домен на той же инфраструктуре

Добавьте в этот же проект второй бизнес-домен, например **обращения в
поддержку** или **складские остатки**. Требования:

- Минимум один новый **source** (таблица, добавленная через новый файл
  `docker/initdb/0X_*.sql`) *и* один новый **seed** — покажите, что
  понимаете, когда что использовать (этап 03).
- Staging-слой (этап 04) и минимум 2 mart'а, включая один `fct_` и один
  `dim_` (этап 05).
- Минимум 3 теста на новую модель, включая один написанный вами
  кастомный generic-тест (этап 06).
- Минимум один написанный вами макрос, используемый где-то в новых
  моделях (этап 07).
- Документация: описания на каждой новой модели/колонке, минимум один
  блок `{% docs %}` и exposure, объявляющий гипотетический
  downstream-дашборд (этапы 11, 13).
- Зелёный CI на PR, который добавляет всё вышеперечисленное (этап 12).

### Вариант B — Углубление в существующий домен

Вместо нового домена — углубитесь в уже существующие данные в стиле
jaffle-shop:

- Добавьте **incremental**-mart с реальной стратегией обработки
  "опоздавших" данных (задание 1 из этапа 09, но реально решённое —
  например, окно допуска по времени).
- Добавьте mart на основе **снапшота**: соедините `customers_snapshot` с
  `fct_orders`, чтобы вычислить "как выглядели данные клиента в момент
  каждого его заказа" (этап 08).
- Установите и используйте `dbt-labs/dbt_expectations` в дополнение к
  `dbt_utils` (этап 10), минимум с 2 его тестами.
- Настройте **Slim CI**: измените `.github/workflows/dbt_ci.yml`, чтобы
  кешировать `target/manifest.json` между запусками и использовать
  `--select state:modified+` (этап 13.3) — это по-настоящему сильное
  дополнение для резюме.

## Как представить результат

Когда закончите:

1. Выполните `dbt docs generate` и сделайте несколько скриншотов графа
   зависимостей — это хороший материал для портфолио.
2. Напишите короткий `FINAL_PROJECT.md` (или дополните корневой
   `README.md`), описав, что вы сделали и зачем, тем же тоном, каким
   говорили бы с интервьюером: какую проблему решает каждая часть, а не
   просто что она делает.
3. Запушьте в GitHub с чистой историей коммитов и смерженным зелёным PR —
   именно PR *является* артефактом; ревьюер должен понять ваши решения из
   диффа и описания, без дополнительных объяснений.

## Самопроверка

Пройдя весь путь, вы должны уметь, без подсказок:

- [ ] Объяснить ELT vs ETL и роль dbt в этой модели.
- [ ] Поднять весь стек с чистого `git clone`, используя только README
      этого репозитория и `make up`.
- [ ] Объяснить материализации и выбрать правильную для новой модели.
- [ ] Объяснить seeds vs sources и обосновать выбор между ними.
- [ ] Написать staging-модель, fact-таблицу и dimension-таблицу с нуля, в
      таком порядке, самостоятельно.
- [ ] Добавить все три вида тестов (встроенный generic, кастомный
      generic, singular) к новой модели.
- [ ] Написать макрос и объяснить `is_incremental()`.
- [ ] Объяснить SCD Type 2 и прочитать историю по таблице-снапшоту.
- [ ] Объяснить, почему incremental-модель быстрее полной пересборки, и
      назвать хотя бы одну incremental-стратегию.
- [ ] Установить и использовать пакет dbt.
- [ ] Сгенерировать и полистать сайт документации dbt.
- [ ] Объяснить, что делает CI-workflow в этом репозитории и зачем.
- [ ] Описать exposures, hooks, Slim CI, semantic layer и dbt Mesh на
      высоком уровне, даже без практической настройки каждого из них.

Если большинство пунктов даётся уверенно — вы прошли путь от "я
попробовал(а) dbt по готовым шагам" до "я умею вести проект на dbt" —
именно такую планку и должен был задать этот проект.
