# 13 — Продвинутые темы

## Цель

Познакомиться с концепциями, которые встречаются в реальных проектах dbt
и на собеседованиях, — за пределами того, что уже отработано руками.

## 13.1 Exposures

**Exposure** объявляет, что нечто вне dbt (дашборд, ноутбук, ML-пайплайн)
зависит от конкретных моделей — см. `exposures:` в
`dbt_project/models/marts/core/_core__models.yml`
(`customer_lifetime_value_dashboard`). Это даёт:

```bash
docker compose exec dbt dbt ls --select +exposure:customer_lifetime_value_dashboard
docker compose exec dbt dbt run --select +exposure:customer_lifetime_value_dashboard
```

...то есть "собрать ровно то, что нужно этому дашборду, и ничего лишнего"
— а сама exposure появляется в графе документации как конечный узел,
поэтому любой, кто смотрит на DAG, видит, что реально потребляет тот или
иной mart.

## 13.2 Hooks

`pre-hook` / `post-hook` (на уровне модели) и `on-run-start` /
`on-run-end` (на уровне проекта, в `dbt_project.yml`) позволяют
выполнять произвольный SQL вокруг модели или запуска — например,
`grant select` после сборки модели или запись метаданных запуска в
таблицу аудита. Попробуйте, просто как эксперимент, добавить:

```yaml
# dbt_project.yml
on-run-end:
  - "{{ log('dbt run finished for target ' ~ target.name, info=true) }}"
```

Выполните `dbt run` и найдите свою строку в логе. После этого верните
изменение обратно, если не хотите его оставлять — hooks мощный
инструмент, которым легко злоупотребить; используйте их только для
того, что обязательно должно выполняться на уровне базы данных (grants,
политики row-level security), для чего у dbt нет специального конфига.

## 13.3 `state:modified` и Slim CI

В большом масштабе пересобирать весь DAG на каждый PR — расточительно.
dbt умеет сравнивать текущее состояние с предыдущим `manifest.json`
(скомпилированным состоянием проекта) и выбирать только изменившееся:

```bash
dbt run --select state:modified+ --state path/to/previous/target
```

Это основа **"Slim CI"**: CI собирает/тестирует только модели, затронутые
диффом PR (плюс всё, что от них зависит ниже по графу), сравнивая с
manifest от последнего успешного запуска в основной ветке. Наш
`.github/workflows/dbt_ci.yml` пока этого не делает (проект достаточно
мал, чтобы в этом не было необходимости) — расширить его до кеширования и
сравнения с предыдущим manifest — хорошая цель для итогового проекта
(этап 14).

## 13.4 Semantic Layer dbt (только обзор)

dbt теперь поддерживает определение **метрик** (например, "выручка",
"активные клиенты") один раз, поверх моделей, с помощью MetricFlow — так
BI-инструменты обращаются к согласованным, управляемым определениям
метрик вместо того, чтобы каждый дашборд немного по-своему реализовывал
"выручку". Для этого нужен dbt Cloud (либо отдельный CLI MetricFlow), и в
этом проекте это не настроено — но вы должны уметь объяснить проблему,
которую это решает: **расхождение определений метрик между дашбордами**,
и что ответ dbt — YAML-блоки `semantic_models:` + `metrics:` поверх уже
существующих marts.

## 13.5 dbt Mesh / мультипроектные настройки (только обзор)

Крупные компании разбивают один гигантский проект dbt на несколько
меньших (по доменам/командам), которые ссылаются друг на друга через
**кросс-проектный `ref()`**, используя уровни доступа моделей
(`access: public|protected|private` в конфиге модели) вместо одного
монолита. Знайте термин и проблему, которую он решает (автономность
команд + независимые деплои), даже без практики построения такого.

## 13.6 Заметки о производительности

- Предпочитайте `incremental` вместо `table`, когда fact-таблица
  становится большой и по большей части только пополняется (этап 09).
- Предпочитайте `ephemeral` для тонких, одноразовых промежуточных CTE,
  которые не нужны отдельным объектом в хранилище — но не злоупотребляйте:
  ephemeral-модели нельзя запросить напрямую, что усложняет отладку.
- Используйте `dbt run --select` и графовые операторы `+` (этапы 04–05),
  чтобы не пересобирать весь DAG во время итеративной разработки.
