# 08 — Снапшоты (SCD Type 2)

## Цель

Понять, зачем нужны снапшоты, и вживую увидеть, как фиксируется история
изменений исходной таблицы.

## Теория

Seeds и sources показывают **текущее** состояние таблицы. Если клиент
обновит email, старый просто исчезнет — будет перезаписан. В большинстве
случаев это нормально. Но иногда нужно ответить на вопрос "что было
верно *по состоянию* на определённую дату" (например: "какой был тарифный
план у клиента в момент, когда он ушёл"). Именно для этого нужны
**снапшоты**: dbt периодически сравнивает исходную таблицу с её же
снапшотом и записывает новую строку при любом изменении, вместо того
чтобы перезаписывать данные.

### Снапшот в этом проекте

```sql
-- snapshots/customers_snapshot.sql
{% snapshot customers_snapshot %}

{{
    config(
        target_schema='snapshots',
        unique_key='customer_id',
        strategy='check',
        check_cols=['first_name', 'last_name', 'email'],
    )
}}

select * from {{ ref('raw_customers') }}

{% endsnapshot %}
```

Есть две стратегии снапшотов:
- **`timestamp`**: у источника есть надёжная колонка `updated_at`; dbt
  использует её, чтобы обнаружить изменения.
- **`check`**: надёжного таймстампа нет; dbt построчно сравнивает
  перечисленные `check_cols` при каждом запуске снапшота. Именно её мы
  используем здесь, так как в `raw_customers` нет `updated_at`.

Каждая таблица-снапшот получает от dbt 4 дополнительные колонки:
`dbt_scd_id`, `dbt_updated_at`, `dbt_valid_from`, `dbt_valid_to`. Строка
с `dbt_valid_to IS NULL` — это текущая версия записи.

## Практика

```bash
make shell
dbt seed              # убеждаемся, что raw_customers существует
dbt snapshot           # первый запуск: у каждого клиента одна строка, dbt_valid_to = null
dbt show --select customers_snapshot --limit 20
```

Теперь имитируем изменение в источнике и снова снимаем снапшот:

```bash
docker compose exec postgres psql -U dbt_user -d dbt_demo \
  -c "update seeds.raw_customers set email = 'maria.i.new@example.com' where customer_id = 1;"

dbt snapshot           # второй запуск
dbt show --select customers_snapshot --limit 20
```

Теперь для `customer_id = 1` должно быть **две** строки: старая, у
которой `dbt_valid_to` выставлен примерно на текущий момент, и новая, у
которой `dbt_valid_to IS NULL` и новый email.

> Обратите внимание: `dbt seed` полностью перезагружает seed-таблицы, что
> сотрёт ваш ручной `UPDATE` — не выполняйте `dbt seed` между двумя
> вызовами `dbt snapshot` выше.

## Задание

1. Повторите последовательность изменение + снапшот для второго
   клиента, затем запросите `customers_snapshot` и вручную восстановите
   полную историю этого клиента по колонкам
   `dbt_valid_from`/`dbt_valid_to`.
2. Объясните, почему здесь выбрана `strategy='check'`, а не `timestamp`.
3. Своими словами: в чём реальная разница между снапшотом и обычной
   incremental-моделью? (Подсказка: подумайте, что происходит со
   **старыми** строками при изменении источника — этап 09 разбирает
   incremental-модели дальше.)
