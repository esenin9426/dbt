# 02 — Структура проекта и материализации

## Цель

Разобраться, за что отвечает каждая папка в `dbt_project/`, и понять
четыре базовые материализации — прежде чем писать свои модели.

## Теория

### Скелет проекта

```
dbt_project/
├── dbt_project.yml     # конфиг проекта: имя, пути, настройки по папкам
├── packages.yml        # сторонние пакеты dbt (этап 10)
├── profiles/            # конфиг подключения (монтируется как ~/.dbt)
├── seeds/               # CSV-файлы, которые dbt загружает как таблицы (этап 03)
├── models/
│   ├── staging/          # очищенные представления 1:1 над sources/seeds (этап 04)
│   └── marts/            # бизнес-таблицы (этап 05)
├── snapshots/           # история SCD2 (этап 08)
├── macros/              # переиспользуемый Jinja (этап 07)
├── tests/               # кастомные generic + singular тесты (этап 06)
└── analyses/            # SQL только для компиляции, для исследований
```

`dbt_project.yml` — единственный источник истины о том, как ведёт себя
каждая папка. Посмотрите на блок `models:`:

```yaml
models:
  dbt_demo:
    staging:
      +materialized: view
      +schema: staging
    marts:
      +materialized: table
      +schema: marts
```

Каждая модель в `models/staging/` по умолчанию — `view`; всё, что в
`models/marts/` — `table`, если только модель не переопределяет это через
`{{ config(materialized='...') }}` в начале своего `.sql`-файла (см.
`models/marts/events/fct_events.sql` — там материализация переопределена
на `incremental`).

### Четыре материализации

| Материализация | Что строит dbt | Когда использовать |
|---|---|---|
| `view` | SQL `VIEW` | Дёшево, всегда свежие данные, подходит для лёгких staging-моделей — простых `SELECT` |
| `table` | `TABLE`, полностью пересобирается на каждом запуске | Marts, к которым часто обращаются / которые должны быть быстрыми для BI |
| `incremental` | `TABLE`, в которую только добавляют/мержат данные, не пересобирая с нуля | Большие, преимущественно append-датасеты (события, логи) — см. этап 09 |
| `ephemeral` | Вообще не строится — встраивается как CTE в то, что на неё ссылается | Тонкие промежуточные шаги, которые не нужны отдельным объектом в хранилище |

### `ref()` и DAG

Модель никогда не зашивает в себя схему/имя таблицы другой модели.
Вместо этого:

```sql
select * from {{ ref('stg_orders') }}
```

`ref()` делает две вещи: резолвит правильные `database.schema.table` для
текущего таргета, **и** сообщает dbt "эта модель зависит от
`stg_orders`" — именно так dbt строит граф зависимостей (DAG) и
автоматически определяет порядок запуска.

## Практика

```bash
make shell
dbt ls                     # список всех ресурсов, известных dbt
dbt ls --resource-type model
dbt list --select staging  # только staging-модели
```

Скомпилируйте проект без обращения к базе данных и посмотрите на
сгенерированный SQL:

```bash
dbt compile
cat target/compiled/dbt_demo/models/marts/core/fct_orders.sql
```

Обратите внимание: вызовы `{{ ref(...) }}` заменены на реальные
`schema.table`, а имена схем берутся из переопределения макроса
`generate_schema_name` (подробно — на этапе 07).
