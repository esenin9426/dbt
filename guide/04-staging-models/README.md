# 04 — Staging-модели

## Цель

Разобраться в конвенции "staging-слоя" и уверенно писать/изменять
staging-модели.

## Теория

Staging-модели — единственные, кому разрешено обращаться к сырым
seeds/sources через `ref()`/`source()`. Все остальные модели строятся
поверх staging-моделей, а не поверх сырых данных напрямую. Это одно
правило даёт много:

- Переименования колонок / приведение типов / конвертация единиц
  происходят **в одном месте**. Если исходную колонку переименуют выше по
  потоку, чинить нужно один staging-файл, а не каждый mart, который её
  использовал.
- Marts читаются как бизнес-логика, а не как чистка данных.
- Сразу понятно, куда смотреть, если колонка выглядит подозрительно: это
  баг очистки данных (staging) или бизнес-логики (marts)?

### Конвенция, принятая в этом проекте

```
dbt_project/models/staging/
├── jaffle_shop/
│   ├── _jaffle_shop__models.yml    -- описания + тесты для stg_*-моделей (sources.yml не нужен: это seeds, ref())
│   ├── _jaffle_shop__docs.md       -- {% docs %}-блоки, на которые ссылается yml выше
│   ├── stg_customers.sql
│   ├── stg_orders.sql
│   └── stg_payments.sql
└── events/
    ├── _events__sources.yml         -- описание source `raw.events`
    ├── _events__models.yml
    └── stg_events.sql
```

Соглашения об именовании: одна staging-модель на одну сырую таблицу,
имя вида `stg_<множественное число>`, одна папка на источник данных, и
ведущее подчёркивание у `.yml`/`.md`-файлов, чтобы они сортировались
выше `.sql`-файлов, которые описывают.

### Что можно делать в staging-модели

Посмотрите на `dbt_project/models/staging/jaffle_shop/stg_payments.sql`:

```sql
with source as (
    select * from {{ ref('raw_payments') }}
),
renamed as (
    select
        payment_id,
        order_id,
        payment_method,
        {{ cents_to_dollars('amount') }} as amount
    from source
)
select * from renamed
```

Здесь допустимо: переименование колонок, приведение типов, лёгкая
конвертация единиц измерения (центы → доллары), возможно `coalesce`
для флага null. **Недопустимо**: джойн с другой таблицей, агрегация или
применение бизнес-правил — для этого есть marts (этап 05).

Staging-модели материализуются как `view` (см. `dbt_project.yml`),
потому что они дёшево пересчитываются и не обязаны быть быстрыми сами по
себе — быстрыми должны быть только marts, построенные поверх них.

## Практика

```bash
make shell
dbt run --select staging   # собирает только staging-модели
dbt run --select stg_payments+   # stg_payments и всё, что зависит от неё
```

Попробуйте графовые операторы с `+`:

```bash
dbt ls --select +fct_orders   # fct_orders и всё, от чего она зависит
dbt ls --select stg_orders+   # stg_orders и всё, что зависит от неё
```
